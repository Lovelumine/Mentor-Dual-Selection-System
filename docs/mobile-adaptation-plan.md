# 移动端适配方案

## 1. 文档目标

本文档用于指导 `Mentor-Dual-Selection-System-Frontend` 的移动端适配实施，目标是：

- 覆盖手机与平板，不再只针对桌面布局。
- 允许对现有应用壳层、导航、内容容器和页面布局做结构性重构。
- 优先输出一套可执行的适配规范，而不是停留在设计原则层面。
- 本轮默认不新增后端 API，优先通过前端布局与组件重构解决问题。

本文档是实施规范，不在本轮直接改业务代码。

---

## 2. 项目现状审计

### 2.1 当前前端结构

当前前端位于 `Mentor-Dual-Selection-System-Frontend`，技术栈为：

- Vue 3
- Vite
- Element Plus
- Pinia
- Vue Router

入口和基础样式位置：

- `src/main.ts`
- `src/assets/base.css`
- `src/assets/main.css`
- `src/views/HomeView.vue`

当前 `index.html` 已配置 `viewport`，但项目内部尚未形成统一的移动端策略。

### 2.2 已确认的响应式问题

结合现有代码审计，当前问题主要集中在以下几个层面。

#### 2.2.1 应用壳层是桌面写法

以下文件体现了壳层级别的固定桌面布局：

- `src/views/HomeView.vue`
- `src/components/HeaderFooterMenu/SideMenuComp.vue`
- `src/components/HeaderFooterMenu/NavHeaderComp.vue`
- `src/components/Home/Relations/RelationsComp.vue`

已确认问题：

- 左侧菜单固定 `200px` 宽度。
- 内容区通过固定 `margin-left: 200px` 绕开侧边栏。
- 部分标题栏与内容容器存在固定偏移，例如 `left: 200px`。
- 头部欢迎区和标题区采用固定宽度，手机端容易溢出或挤压。

这意味着当前布局不是“根据可视区域排布”，而是“先按桌面写死，再让内容去适应”。

#### 2.2.2 页面内部大量依赖固定像素值

以下页面和组件问题最明显：

- `src/components/Home/SelectTeacherComp.vue`
- `src/components/Home/TeachResumeComp.vue`
- `src/components/SigninComp.vue`
- `src/views/ForgetPwdView.vue`
- `src/views/PersonalView.vue`
- `src/components/Personal/MyDetailComp.vue`
- `src/components/Home/StudentList/StudentListPage.vue`

已确认现象：

- 大量使用固定宽高，如 `400px`、`500px`、`700px` 等。
- 多处依赖绝对定位。
- 弹窗、卡片、筛选栏、表单默认按桌面横向排布。
- 表格在小屏上没有降级策略。

#### 2.2.3 缺少统一响应式状态

当前项目中没有统一的：

- 设备类型状态
- 断点工具
- 侧边栏移动模式
- 表格/卡片切换规则
- 弹窗移动端宽度规范

项目内只有零散的页面级 `@media` 补丁，并未形成全局规则。

#### 2.2.4 表格与高信息密度页面不适合手机

以下页面在手机端问题会最严重：

- 学生列表
- 导师列表
- 师生关系页
- 学生申请与审批页
- 历史关系与管理列表页

当前问题包括：

- 列过多，缩放后可读性差。
- 搜索区和筛选区横向排布，容易换行错乱。
- 弹窗中的长表单和长文本没有适配规则。

### 2.3 当前代码中的结构性风险

在适配移动端前，需要把以下事实视为既定条件：

- 当前壳层偏移逻辑是后续移动端改造的最大阻力。
- 关系页、导师卡片页和选导师页已有不少局部重构，后续要收口成统一规范。
- 项目中仍存在部分历史遗留组件与新组件并存的情况，适配时需要优先面向当前真实路由使用的页面。

## 3. 外部项目研究摘要

本方案参考并对比了以下后台项目：

- `vue-element-admin`
- `vue3-element-admin`
- `soybean-admin`

研究重点不是视觉样式，而是它们的响应式组织方式。

### 3.1 vue-element-admin

重点参考位置：

- `src/layout/index.vue`
- `src/layout/mixin/ResizeHandler.js`
- `src/styles/sidebar.scss`

可借鉴结论：

- 用全局 `device` 状态区分 `desktop / mobile`。
- 通过统一断点切换侧边栏行为。
- 手机上侧边栏改为抽屉，并带遮罩。
- 主内容区不再依赖固定桌面偏移，而是跟随设备状态切换。

### 3.2 vue3-element-admin

重点参考位置：

- `src/layouts/BaseLayout.vue`
- `src/store/modules/app.ts`

可借鉴结论：

- 用全局 store 管理侧边栏打开状态和设备状态。
- 手机端内容层、侧边栏层、遮罩层有清晰分工。
- 壳层适配放在布局组件里，不把责任散落到业务页面。

### 3.3 soybean-admin

重点参考位置：

- `src/store/modules/app/index.ts`
- `src/hooks/common/table.ts`
- `packages/materials/src/libs/admin-layout/index.module.css`

可借鉴结论：

- 使用统一断点工具，而不是散落媒体查询。
- 表格、分页、抽屉宽度都按设备状态降级。
- 手机端默认精简密度，平板端保留更多桌面能力。

### 3.4 对本项目的启发

结合三者，本文档为本项目确定如下默认策略：

- 不采用“每个页面各自写媒体查询”的方式。
- 必须引入全局设备状态。
- 手机端侧边栏改抽屉层并带遮罩。
- 平板端侧边栏默认折叠为图标列，可展开为抽屉。
- 桌面端保留固定侧边栏，但不再用硬编码 `left: 200px` 和 `margin-left: 200px` 推动布局。
- 表格、筛选栏、弹窗、分页都要定义统一的移动端降级规则。

## 4. 本项目移动端适配总策略

### 4.1 断点定义

全局断点固定为：

- 手机：`<= 767px`
- 平板：`768px - 1023px`
- 桌面：`>= 1024px`

后续任何组件和页面的适配，都必须基于这一套断点，不允许自行定义第二套标准。

### 4.2 全局设备状态

前端需要提供统一设备状态：

- `device = mobile | tablet | desktop`
- `sidebarMode = drawer | collapsed | fixed`

建议由一个统一响应式工具或 store 提供，不允许页面自己直接基于 `window.innerWidth` 写分叉逻辑。

### 4.3 壳层行为

#### 手机

- 左侧菜单默认隐藏。
- 头部显示菜单按钮。
- 点击菜单按钮后，侧边栏以抽屉形式从左侧滑出。
- 抽屉出现时必须有遮罩。
- 内容区全宽，不再预留固定侧栏空间。

#### 平板

- 左侧菜单默认折叠为窄图标列。
- 点击展开时以抽屉或半展开侧栏方式显示完整菜单。
- 内容区保留有限边距，但不采用桌面版固定 `200px` 左偏移。

#### 桌面

- 左侧菜单固定展开。
- 内容区不再写死 `margin-left: 200px`，而是由布局容器统一分配。

### 4.4 通用 UI 规则

全站统一遵守以下规则：

- 触控目标不小于 `44x44`。
- 主内容区水平边距按设备断点递减。
- 弹窗：
  - 手机：全屏或 `90vw`
  - 平板：`min(90vw, 720px)`
  - 桌面：保留原常规宽度
- 表单默认单列，桌面端才允许双列或多列。
- 顶部长标题允许截断、省略和换行，但不允许顶破布局。
- 搜索与筛选区必须允许换行或折叠。
- 分页在手机端减少页码数量与外围留白。

## 5. 页面级改造矩阵

### 5.1 登录 / 找回密码 / 注册

涉及：

- `src/components/SigninComp.vue`
- `src/views/ForgetPwdView.vue`
- 相关注册/认证页

适配要求：

- 手机端采用单列居中布局。
- 去掉绝对定位和固定高度容器。
- 按钮改为纵向堆叠或紧凑横排。
- 标题、副标题和表单区域允许自然换行。

### 5.2 应用壳层

涉及：

- `src/views/HomeView.vue`
- `src/components/HeaderFooterMenu/SideMenuComp.vue`
- `src/components/HeaderFooterMenu/NavHeaderComp.vue`
- `src/components/Home/Relations/RelationsComp.vue`

适配要求：

- 壳层优先重构。
- 把“侧栏固定宽度 + 内容固定偏移”的模式改成布局流模式。
- 固定标题条与内容区的关系重新梳理，避免在手机端出现层叠遮挡。

### 5.3 导师卡片相关页

涉及：

- `/select_teacher`
- `/teach_resume`

对应组件：

- `src/components/Home/SelectTeacherComp.vue`
- `src/components/Home/TeachResumeComp.vue`

适配要求：

- 手机端卡片改为单列。
- 头像、名字、职称、按钮、研究方向纵向重排。
- 卡片背景图保留，但不能干扰正文可读性。
- 长简介和研究方向需支持折叠或截断展示。

### 5.4 学生列表 / 导师列表

涉及：

- 学生列表页
- 导师列表页

适配要求：

- 手机端默认切换为卡片列表。
- 平板端允许保留表格，但必须支持横向滚动且减少列数。
- 搜索区改为可换行结构。
- 操作按钮不得挤压表头或正文。

### 5.5 师生关系页

涉及：

- 管理员关系分组页
- 学生关系页
- 导师关系页

适配要求：

- 管理员页保留“按导师分组”思路，但手机端改为单列分组卡片。
- 组内详情默认折叠，避免一屏信息过载。
- 学生/导师页新增的时间信息、历史关系信息必须在小屏上仍可读。

### 5.6 个人中心与编辑页

涉及：

- `src/views/PersonalView.vue`
- `src/components/Personal/MyDetailComp.vue`

适配要求：

- 详情展示与编辑表单统一单列。
- 照片与卡片背景区域不再使用固定大尺寸。
- 空图片状态必须显示占位，不允许出现浏览器坏图。

### 5.7 各类弹窗

涉及：

- 选择导师
- AI 生成申请理由
- 审核详情
- 管理员确认弹窗
- 删除/转出/重置/恢复确认弹窗

适配要求：

- 弹窗统一进入响应式规范。
- 手机端优先全屏或接近全屏。
- 弹窗内长文本、表单和按钮区按纵向排布处理。

## 6. 公共组件与实现约定

### 6.1 统一响应式工具

应新增统一的响应式工具层，用于：

- 暴露当前设备类型
- 暴露当前侧边栏模式
- 提供常用断点判断

推荐形式：

- `useResponsive()` composable
- 或一个轻量 `layout/app` store

### 6.2 布局组件职责

布局层需要承担以下职责：

- 决定侧边栏模式
- 控制头部菜单按钮显示
- 控制抽屉遮罩
- 统一内容区边距与可用宽度

业务页面不应再自己控制布局偏移。

### 6.3 列表展示模式

列表型页面统一支持两种展示模式：

- `table`
- `card`

规则固定为：

- 手机优先 `card`
- 平板优先 `table`
- 桌面固定 `table`

### 6.4 弹窗模式

弹窗统一支持：

- `desktop`
- `mobile-fullscreen`

切换依据只来自统一设备状态。

### 6.5 搜索与筛选区

筛选区统一规则：

- 手机：纵向堆叠
- 平板：两列换行
- 桌面：横向排列

不再允许页面自己通过固定宽度拼接搜索栏与筛选器。

### 6.6 后端接口约束

本轮移动端适配默认：

- 不要求新增后端 API
- 不要求修改权限逻辑
- 不要求变更业务数据结构

如果个别页面需要显示时间、状态或历史记录，优先通过前端布局容纳，而不是因移动端重新拆接口。

## 7. 实施优先级与阶段路线图

### Phase 1：壳层与断点体系

目标：

- 建立统一断点
- 建立全局设备状态
- 重构头部、侧栏、内容容器

完成标准：

- 手机端能正常打开/关闭侧边栏
- 平板端侧边栏可折叠
- 桌面端布局不回退

### Phase 2：高频核心页

优先改造：

- 登录页
- 选导师页
- 导师卡片页
- 学生列表
- 导师列表

完成标准：

- 手机端可单手操作
- 卡片与列表不溢出
- 搜索与筛选不挤压

### Phase 3：关系页与弹窗体系

优先改造：

- 管理员关系页
- 学生关系页
- 导师关系页
- 各类审核/确认/申请弹窗

完成标准：

- 手机端关系页可读
- 长表格有降级方案
- 弹窗内容不超视口

### Phase 4：剩余页面与统一 QA

范围：

- 个人中心
- 公告页
- 上传页
- 历史记录与其他长表单页面

完成标准：

- 手机/平板无严重横向滚动
- 深色模式、浅色模式都可用
- 不破坏现有桌面业务流程

## 8. 测试矩阵与验收标准

### 8.1 视口矩阵

至少覆盖以下视口：

- `390x844` 手机竖屏
- `430x932` 大屏手机
- `768x1024` 平板竖屏
- `1024x1366` 平板横屏
- `1280px+` 桌面

### 8.2 核心验收点

所有核心页面都应满足：

- 页面主布局不出现非预期横向滚动。
- 侧边栏在手机/平板模式下可打开、关闭、遮罩正确。
- 核心页面按钮、输入框、分页可正常点击。
- 表格页在手机上不出现“缩成蚂蚁字”的情况。
- 弹窗在手机端不超出视口。
- 深色模式与浅色模式都要验证。
- 不破坏现有桌面端路由结构与业务流程。

### 8.3 重点回归页面

建议每轮改造都至少回归：

- `/`
- `/select_teacher`
- `/teach_resume`
- 学生列表
- 导师列表
- `/relations`
- `/personal`
- 申请/审核弹窗相关页面

## 9. 默认假设

- 文档先作为实施规范，不在本轮直接落业务代码。
- 文档路径固定为 `docs/mobile-adaptation-plan.md`。
- 范围覆盖手机和平板，不单独兼容超老旧浏览器。
- 允许重构应用壳层、导航和页面布局，但不主动改业务规则和后端接口。
- 优先保证“能用、稳定、一致”，其次再做更激进的视觉优化。

---

## 10. 建议的实施顺序结论

如果后续正式开始改造，建议严格按以下顺序推进：

1. 先改应用壳层，不先改业务页。
2. 再改导师卡片页、选导师页、列表页。
3. 再收口关系页与弹窗体系。
4. 最后统一清理剩余页面的历史固定宽度、绝对定位和媒体查询补丁。

这样可以避免：

- 业务页面各自适配但壳层仍是桌面结构
- 页面越改越碎
- 同一项目出现 2 到 3 套并存的响应式规则

本项目后续所有移动端改造，应以本文档为准。
